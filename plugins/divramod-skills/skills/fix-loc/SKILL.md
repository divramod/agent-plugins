# fix-loc

A loop session running in its own Claude session over one repository. It only scans, starts and watches, so its
context stays small over days; the refactoring happens in fresh servant sessions, one unit at a time. The rule is
the repository's `.adr/small-files.md` (hal2); the evidence and the ideas behind the loop are in hal2's
[research 0021](https://github.com/divramod/hal2/blob/main/research/0021-optimal-code-size-limits-for-humans-and-ai-agents/research.md).

- `S=<skill-dir>/scripts`, `L="python3 $S/loop.py"`, `C="python3 $S/scan.py"`.
- The repository is the one of the session's working directory (`--repo .`); run the loop session in a checkout of
  it that does no other work.
- State (the running servant, the coordinator and step values, history with code lines before and after, blocked
  units, the loop's start) lives in
  `~/skills/fix-loc/<repo>/state.json` (`FIX_LOC_ROOT` overrides `~/skills/fix-loc`).
- The servant's prompt is [servant-prompt.md](servant-prompt.md); `loop.py` fills in the unit, its files and the limit.
- Settings per repository: `.hal/fix-loc.toml` (`limit`, extra `exclude` globs, extra `units` globs).
- **Never ask the user anything in a tick.** When something needs the user, push a notification (`PushNotification`).

| Call | Does |
|---|---|
| `/fix-loc` | one [tick](#the-tick) now |
| `/fix-loc start [<minutes>] [<values>]` | [start the loop](#the-loop) in this session (default every 15 minutes), then one tick; `<values>`: `--coordinator-model <id>` (`--model`; default `claude-sonnet-5-5`), `--coordinator-effort <level>` (default `medium`), `--step-model <alias>` (default `sonnet`) |
| `/fix-loc stop` | delete this session's fix-loc cron job, `$L record --repo . --stopped`; a running servant keeps running to its landing |
| `/fix-loc status` | `$L status --repo .`: the servant (unit, slot, plan), blocked units, the last landings with lines before/after |
| `/fix-loc scan` | `$C scan --repo .`: every unit over the limit, hotspot first, busy ones last |
| `/fix-loc next` | `$L tick --repo . --dry-run`: what the next tick would do, the next unit's files, start command and servant prompt; writes nothing |
| `/fix-loc h`, `/fix-loc help` | print this table and stop |

## The loop

1. `bash $S/check-prerequisites.sh`. Exit 1: run `bash $S/install-prerequisites.sh` once.
2. Check this session holds no fix-loc job yet (`CronList`). Then `CronCreate`:
   - `cron`: `4,19,34,49 * * * *` for 15 minutes, off the :00 and :30 marks; another interval spreads its minutes
     the same way;
   - `prompt`: `/fix-loc`, with the values the user gave (`/fix-loc --coordinator-model <id> --step-model opus`);
   - `recurring`: true.
3. `$L record --repo . --started`.
4. Say that the loop runs while this session is open and idle, one unit at a time, until `/fix-loc stop`.
5. Run one tick.

## The tick

`$L tick --repo . --json [<values>]`. A value not given is the one `state.json` keeps from an earlier tick, else its
default. Its `action`:

| Action | Means | Do |
|---|---|---|
| `wait` | the servant works on its plan | print one line (`fix-loc <time>: <unit> in slot <NN>, <reason>`) and end the turn |
| `next` | the last plan landed (or none ran): a servant was started for `unit` | one line: unit, slot, files |
| `idle` | no unit is over the limit, or every one is busy or blocked | one line; keep the loop running (new code may grow a file) |
| `paused` | the servant's landing holds the merge queue after a failure | one line; nothing new starts until it clears |

`notify` lists what needs the user (a blocked servant, a paused landing, a unit given up after two plans that left it
over the limit): send each as one `PushNotification`. A servant counts as blocked when its agent is gone without
landing, a dialog waits over 30 minutes, or it is idle over 60 minutes without landing; its unit is skipped 7 days
and the next unit starts. A blocked servant is left as it is for the user to look at.

`rearm: true`: the cron job is 6 days old and recurring jobs expire after 7. `CronDelete` it, `CronCreate` it again
as in [the loop](#the-loop), and `$L record --repo . --started`.

Exit 2: a tool is missing; run `bash $S/install-prerequisites.sh`, then tick again.

## The servant

`loop.py` starts it with create-worktree-session's `create.py --repo <main checkout> --from 30 --model
<coordinator model> --effort <coordinator effort> --exact --prompt <servant prompt>`: a fresh agent in the first
slot from 30 with no session and no work, in a hal2 terminal host. The servant is its plan's coordinator, Sonnet by
fix-loc's own rule (skills plan 0015's D15): it runs /mfm, creates its plan with `plan.py new "fix-loc: <unit>"
--autogenerated fix-loc`, names it to the loop with `$L claim --repo . --plan <slug>`, autogrills it once and runs
it with `/plan n` to its automatic landing (`Landing: auto`), every step in one subagent at its row's Model and
Effort (by default the step model, medium, `1m`), each sized under 35% of its Window. The plan covers the whole unit (every file over the limit), in this order: delete dead code,
extract functions over 50 code lines, move inline test modules to their own files, split what is still over along
cohesive seams; behaviour unchanged; the docs agents read updated; its last done-when is
`$C check --repo . <unit> --worktree`. There are no exemptions: a file over the limit gets split.

After the landing, the next tick counts the unit on the default branch again, records before and after, stops the
servant's terminal host and starts the next unit's servant. A unit still over the limit after two landed plans is
skipped 30 days.

## Rules

- **Never do these:** run `/mtm` or `merge-to-main` (the servant's plan lands itself); touch a landing or the merge
  queue; answer a servant's dialog or type into its pane; start a second servant while one runs; edit code yourself.
- **One unit at a time.** The next servant starts only after the previous plan landed or was blocked.
- **Keep the session small.** Quiet ticks print one line. When this session's context passes 50%, notify the user to
  restart the loop session (`/clear`, then `/fix-loc start`); all state lives in files.
- Improvements to fix-loc itself go into a report to the user, never into a servant's plan.
