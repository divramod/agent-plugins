# Woken for wagon trains (trains)

The tick forms, starts and settles the trains itself (the ready wagons in queue order, the trial merge, the own
field as carrier, the detached landing, "in the barn" to every car, a conflicting wagon unhitched with its reason:
[merge-train](../subskills/merge-train/SUBSKILL.md)); a servant's field (one holding `plans/LEAD`) never rides, a foreman's wagon from any field 00-99 does. No car rides without its light gate
checks (names, records) green on its hitched head (`proof.py`): a red one is unhitched and told the finding lines, a
field not at its hitched head waits ("no proof yet"), never a wake. Those are the drop-outs before forming: a formed
train is frozen (plan 0360 D3): nothing leaves it, a wagon that hitches meanwhile rides the next one, and no wait
limit ends a waiting or red train (D7); the session's `unhitch` of its car and `engine.py breakup` are refused. Only
the user's own command passes `--by-user`; never pass it yourself. You get what needs judgment. Check it
is still true (`python3 $S/tollman.py train --dry-run`, `hal2-cli-git worktree queue --json`), act, then log it:
`python3 $K/farmer/scripts/mtm_scan.py record <kind> <slot> "<what you did>" --note "<why>" --role tollman`.

Before you act: read [rules.md](rules.md), then the learnings (`python3 $S/learnings.py rules`, the file `roles/tollman/learnings.md`) and
apply their rules. After you handled a red train, an error or a by-hand fix, write one entry
(`python3 $S/learnings.py add --case ... --cause ... --rule ... --code y|n`, [SKILL.md](../SKILL.md#act)).

| Kind | Do |
|---|---|
| `train-red` | The train's landing still runs and its land run has a red job (watch.py): the barn's red, or a car's red whose culprit the code could not name (one named car gets its fix order by code, early_order.py, plan 0383 D5), the same evidence as `train-failed` below. Act on it now as there (the fix waits on the same train); the landing ends red by itself and wakes nobody again for this run. One whose text says "red after its merge" (post_merge.py, plan 0383 step 6): the train is in the barn, nothing holds the next train; when you name the car, `python3 $S/tollman.py order <car> --post <train> --why "<job>: <error>" --run <url>`, its fix rides the next train |
| `train-failed` | The train's landing did not land; the code's triage (`triage.py`) names its kind and evidence (`python3 $S/tollman.py triage <run>` prints it again with the log's tail). A runner fault never wakes you: the code retries it on a fresh run. **`car_red`, one car broke it** (the evidence lists each car's files against the train's base, the red job's first failed step and the failing tests; reproduce the job with `code/bash/scripts/gate/main.sh <job> --branch origin/main` where the repository has it): the train is frozen and waits for that car's fix; record the cause (`mtm_scan.py record`) and give its foreman the fix order, `python3 $S/tollman.py order <field> --why "<failing job and cause>"` (the code sends the acked message with the commands; plan 0360 D6); unhitch nothing. When the foreman's `ack <id>: done fixed <sha>` arrives, record it (`acks.py ack <id> done fixed <sha> --role tollman`): the round runs `tollman.py fixed` by code (or run `python3 $S/tollman.py fixed <field> <sha>` yourself); a refused fix keeps the order open and its foreman is told why. Your judgment says it is no car after all (a test that fails alone, a fault the patterns missed): `python3 $S/tollman.py retry --why "<why>"` sends the same train again whole. **`main_red`, the barn itself is red** (the same job red in another slot's earlier land run on the same barn head): the train waits and the barn is fixed in this same train (D29): `python3 $S/tollman.py order main --why "<job and cause>"`, then a hand of yours fixes it on `tollman-train-fix` from the carrier's head, you switch back to the carrier and run `python3 $S/tollman.py fixed main <sha>`. No triage (a conflict, no run): name the cause as above |
| (none) | A smuggle pauses the train (plan 0360 step 18): you are never woken for it. The pause is a tick.log line, its cancelled run no red; a resume conflict or a red on a smuggle's files is a fix order to the smuggling field sent by code (`tollman.py order <slot> --smuggle`), answered as any fix order. A `fix-refused` or `train-stuck` for such an order is acted on as below |
| `fix-order-main` | Your own `order main` (D29): the barn's red is fixed by a hand of yours, in the train's worktree (the item's `where`, plan 0375 D5; with no train standing the tollman's field): `git switch -C tollman-train-fix <base>` (the item's base), the fix, a commit, `git switch <carrier>`, then `python3 $S/tollman.py fixed main <sha>`. With a red train standing the same cars land again on the merge; with no train (own_fix.py) the fix is merged into the field's own branch and the next train, which waits for it, takes it as its first car |
| `main-red` | The duty `mainred` (plan 0360 step 8): `main` itself is red outside a train (the newest run of a workflow on the default branch) and its failed log is no transient fault, or it was red again after the code's one rerun. Judge the evidence's `log_tail` (`gh run view <run> --log-failed` for all of it). A fault in the code: `python3 $S/tollman.py order main --why "<job and cause>" --run <url>`, then as `fix-order-main`. A fault outside the code (a runner, a secret, GitHub): no order; leave the farmer a board note (`board.py post --kind note --from tollman-<repo> --to farmer-<repo> --text ...`; it reads it when it asks) |
| `fix-refused` | A foreman's `fixed <sha>` did not pass (not on `origin/<NN>-train-fix`, not from the order's base, or it does not merge): the code told the foreman why and the order stays open. Act only when the foreman cannot fix it (leave the farmer a board note (`board.py post --kind note --from tollman-<repo> --to farmer-<repo> --text ...`; it reads it when it asks)) |
| `train-runner-broken` | 3 runner faults in a row, each retried by code: the runner looks broken. Look at the runners (docs/ci.md), leave the farmer a board note (`board.py post --kind note --from tollman-<repo> --to farmer-<repo> --text ...`; it reads it when it asks), then `python3 $S/tollman.py retry --why runner` |
| `train-failed`, status `pretest_red` | The local pretest before the push was red: nothing was pushed, no run. The item names the job and the suspect car(s), whose own range selects the job. Read the job's output in `roles/tollman/train-pretest.log` and reproduce it in the own field with `code/bash/scripts/gate/main.sh <job> --branch origin/main`. Then as above: the named car's or the barn's red waits for its fix, `retry` when it is not a car and may pass now (a flaky job: a retry pretests again). The red is the Mac's, not a car's (it fails on this Mac only, e.g. a tool or path of this machine, while CI's job passes): `python3 $S/tollman.py retry --skip-pretest --why "<why>"`, the train lands without its pretest |
| `train-failed`, the yard as the cause | The train's `Worktree:` trailer names `main` (the yard) and the failing task's files are the yard's commit (`train.jsonl`'s `yard` line names them; the dry run's `yard: placed:` lines show what rides next): the train waits for the yard's fix: leave the farmer a board note (`board.py post --kind note --from tollman-<repo> --to farmer-<repo> --text ...`; it reads it when it asks) naming the files that fail. Only the user's own `tollman.py unhitch yard --why "<job and cause>" --by-user` takes the yard's car out (its files stay in the yard, out of every train until they change). Never edit the yard's files |
| `train-stuck` | An engine verb failed (the item names the verb and the command). Run the command to see why, then `python3 $S/tollman.py train --dry-run`. A leftover mark without a train of ours: `python3 $S/engine.py breakup --why "<why>"` clears it; a train that stands is frozen, the breakup refuses it (only the user's `--by-user`): fix what the command names (a car the field lacks merges at the next restart). Not fixable here (a git or `hal2-cli-git` fault): notify the user |

**Composition, order and the alone rule are yours** ([wagon-master-decides-trains](https://github.com/divramod/hal2/blob/main/.adr/wagon-master-decides-trains.md)): which wagons ride together, in what order,
what rides alone. Decide by the trial merge and the queue order (a tie goes to the wagon that hitched first), record it
(`mtm_scan.py record` as above, with the reason in `--note`), report it to the foreman it concerns, and never ask the
user; a question only the user can answer goes into your own store (SKILL.md, "Your questions") and the work goes on.

Never: stop a landing that runs or has merged into the default branch, force-push, edit, reset or merge another
field's branch yourself (the foreman restocks and fixes its own crop), unhitch a car of a formed train or break one
up (the commands refuse it; `--by-user` is the user's alone). A wagon you unhitch is told why by the code; add nothing unless the cause needs the foreman's
judgment. Messages to a foreman that carry a question go through `acks.py instruct <slot> "<text>" --role
tollman`.
